01What is being tested, and what is not

The FPGA cannot translate anything on its own, and pretending otherwise would make every number below meaningless.

The fabric holds one encoder layer's matmul chain and its softmax. It has no embedding table, no decoder, no beam search, and not enough block RAM to hold a single 512×512 weight matrix — that is 256 KB against a 225 KB device. So the claim under test is narrower and more useful than "it translates":

The claim. Drive the real opus-mt-en-ar weights and the real token embedding for “Hello” through six passes of the RTL encoder layer, let the PS do the elementwise work between passes, and the resulting encoder state still decodes to the correct Arabic token.

Everything else — embeddings, the decoder, weight streaming — is the processing system's job, which is what the Zynq part is for. The original README says so itself: “an ARM Cortex-A9 on the PS side orchestrates DMA, tiling and token streaming.”

02Where the line between fabric and processor falls

Not by what fits, but by where the arithmetic actually is.

Programmable logic

3.1 M
multiply-accumulates per token, per layer
  • Q, K, V and output projections
  • QKᵀ scores
  • softmax — exp table, no divider
  • attention × V
  • both FFN layers
  • requantisation and saturation

Processing system

13 K
elementwise operations per token, per layer — 0.4%
  • projection biases
  • swish (SiLU) between FFN layers
  • residual add
  • two layer normalisations
  • quantisation scale selection
  • weight streaming and job issue

Layer normalisation is the interesting case. It can be built in fabric — a mean is a shift when D = 512, the variance is one DSP, the reciprocal square root is a table. It is left on the PS anyway, because it is 0.4% of the arithmetic and 100% of the dynamic-range difficulty, and because the PS has to touch every tensor at the layer boundary regardless — it is already streaming the weights in. The round trip is roughly 20 µs of DMA against several milliseconds of fabric compute.

Measured consequence of that boundary. Counted from the generated job stream, a layer loads 131,072 weight-window rows — 1,048,576 bank words at 32 bits per cycle, 10.5 ms at 100 MHz — against roughly 232,000 cycles of actual compute. The design is weight-bandwidth bound by about 4.5:1. Adding fabric arithmetic would not make it faster; widening the weight path would.

05The rule that governed which fixes were allowed

Run 9 closed timing at +58 picoseconds. That is closure with no margin worth relying on.

Every change was classified before it was made, and the classification decided whether it was permitted:

ClassTiming exposurePolicyUsed for
Control pathnone — FSM states, counters, drain lengthsfree9 of the 13 fixes
New register stageadds latency, not path depthfreestaging pipeline, exp data alignment
Constant → registersame net, different sourcelowprogrammable requant multiplier
New 2:1 muxone LUT level on an existing pathjustifyMAC flush zeroing, score readback
Deepen existing stagedirectly consumes slackavoided—

Two muxes were added. Both sit between a block RAM output and a register input, on paths with most of a 10 ns period spare — not on the writeback or softmax cones where run 8's critical paths lived. The programmable requant multiplier replaced a hardwired constant on a net that already fed the reciprocal multiplier, so it changes the source of a value rather than the depth of any cone.

Not yet re-measured. These are arguments, not results. The design has not been back through Vivado since the fixes. Every claim in this section is an expectation until a run reports WNS, and at +58 ps of starting margin the expectation is worth exactly what a re-run costs.

06Two things the fabric now does that it could not

Reduction chunking

The weight window holds 1,024 rows. The FFN output layer reduces over 2,048, so it did not fit even for a single output tile — and the projections (512×512 = 256 KB) never fit at all. The sequencer now takes acc_clr and acc_wb: a long reduction is issued as several jobs with a weight reload between them, and the accumulator survives across them. Only the last chunk writes back.

A programmable requantisation multiplier

Output scale used to be a power of two, because rq_shift was the only control. Softmax cannot live with that. exp_rom is indexed as (max − s) >> 4 over a table of exp(−i/256), so a score LSB means 2⁻¹² in natural-log units. Miss that scale by a factor f and the hardware computes exp(−z/f) — the attention runs at the wrong temperature, silently, with no failing endpoint anywhere. The 18-bit multiplier that already existed for the reciprocal now takes a programmable value and hits the required scale to about 17 bits instead of to the nearest octave.

The dominant loss is the FFN, which is expected: it is the widest reduction and the only place a nonlinearity sits between two int8 quantisations. The requantisation truncates rather than rounds to nearest, which costs a systematic half-LSB per stage — the cheapest available accuracy improvement and a candidate for the next revision, at the cost of one adder in the writeback.
